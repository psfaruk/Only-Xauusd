5. PHASE 2 — ESTABLISH THE VISUAL IDENTITY

Create a unified design identity using these four primary visual themes:

1. Sky blue.
2. Sunlight and warm amber.
3. Dark graphite/navy.
4. Clean white.

The overall direction should combine a modern financial terminal with a clean, premium analytics dashboard.

The interface must be visually attractive without sacrificing readability, chart visibility, or operational clarity.

5.1 Color system

Use centralized design tokens. Do not scatter arbitrary hex colors across individual components.

Suggested initial palette:

Token| Suggested value| Purpose
Primary sky blue| "#38BDF8"| Primary actions, active navigation, highlights
Deep sky blue| "#0284C7"| Primary buttons on light surfaces
Pale sky blue| "#E0F2FE"| Light-theme selection and informational backgrounds
Dark background| "#0B1220"| Main dark-theme background
Elevated dark surface| "#111C2E"| Sidebar and major panels
Dark card surface| "#162338"| Cards and secondary surfaces
Clean white| "#FFFFFF"| Light-theme backgrounds
Light surface| "#F4F8FC"| Light-theme panels
Main dark text| "#172033"| Light-theme text
Main light text| "#EAF2FF"| Dark-theme text
Muted text| "#64748B"| Secondary text on light surfaces
Dark-theme muted text| "#9FB0C7"| Secondary text on dark surfaces
Sunlight amber| "#FBBF24"| Highlights, selected accents, warning emphasis
Success green| "#22C55E"| Successful operations and validated states
Danger red| "#EF4444"| Errors and bearish/downward market indicators
Border light| "#DCE5F0"| Light-theme dividers and borders
Border dark| "#26364D"| Dark-theme dividers and borders

These are starting values, not an excuse to ignore contrast testing. Refine them after checking text contrast, chart visibility, active states, and visual balance.

Important color semantics

- Sky blue is the primary brand accent.
- Sunlight amber is a restrained secondary accent.
- Dark graphite and navy create a professional terminal environment.
- White and soft gray create clean light-mode surfaces.
- Green and red communicate market direction and status, not decorative branding.
- Never use color alone to communicate a critical state; combine it with a label or icon.

Avoid excessive gradients, glowing borders, neon colors, glassmorphism, blur effects, and decorative animations.

Use gradients sparingly, mainly in subtle hero or overview accents.

5.2 Theme modes

Implement a coherent dark and light theme if the existing architecture supports it.

Requirements:

- Dark mode should be the primary trading-terminal experience.
- Light mode must remain fully designed, not merely an inverted dark theme.
- All surfaces, borders, text, menus, popovers, tooltips, charts, and dialogs must follow the active theme.
- Persist the user's theme preference using the project's existing or appropriate theme mechanism.
- Avoid hydration mismatches and theme flashes.
- Respect system preferences where appropriate.
- Ensure charts update their visual configuration when the theme changes.

Do not add a theme toggle that changes only the page background.

6. PHASE 3 — CREATE A COMPLETE DESIGN SYSTEM

Create a documented, maintainable design system.

Centralize tokens for:

- Colors
- Typography
- Font sizes
- Font weights
- Line heights
- Spacing
- Border radii
- Border widths
- Shadows
- Layout widths
- Sidebar dimensions
- Header heights
- Z-index layers
- Transition durations
- Focus rings
- Responsive breakpoints
- Chart colors
- Status colors

Use CSS custom properties and the styling approach supported by the existing project.

Use Tailwind utilities where appropriate and reusable component variants for repeated patterns.

Do not build every page using independent custom CSS.

Typography

Choose a professional, readable sans-serif font that supports the required languages.

Recommended hierarchy:

- Main page title: 26–32 px desktop.
- Section title: 18–22 px.
- Card title: 14–16 px.
- Body text: 14–16 px.
- Secondary labels: 12–14 px.
- Market price: 24–36 px, depending on context.
- Small technical metadata: generally 11–12 px, never too small for critical information.

Use consistent font weights and line heights.

Use tabular numerals for prices, timestamps, spreads, and other rapidly changing numeric values where appropriate.

Avoid oversized text in dense trading panels.

Spacing system

Use a consistent spacing scale based on 4 px increments.

Suggested patterns:

- Small inline gaps: 4–8 px.
- Control spacing: 8–12 px.
- Card internal spacing: 16–20 px.
- Section spacing: 20–28 px.
- Major page separation: 24–32 px.
- Desktop outer page padding: 24–32 px.
- Tablet outer page padding: 16–24 px.
- Mobile outer page padding: 12–16 px.

Choose values consistently and centralize repeated patterns.

Radius and elevation

- Small controls: 6–8 px radius.
- Inputs and standard buttons: 8–10 px radius.
- Cards and panels: 12–16 px radius.
- Large dialogs: 16–20 px radius.

Use subtle borders and restrained shadows.

Avoid making every element a floating rounded card. Use clear grouping and deliberate visual hierarchy.

11. PHASE 8 — BACKEND-TO-FRONTEND CONTRACT PRESERVATION

This is the most important engineering requirement.

The UI must become better without breaking the application behind it.

11.1 Build an API contract inventory

Before frontend integration changes, inspect every relevant endpoint.

For each endpoint, record:

- Path.
- HTTP method.
- Authentication and authorization.
- Request schema.
- Response schema.
- Error response format.
- Side effects.
- Cache behavior.
- Consumers in the frontend.
- Existing tests.

Inspect all existing market-data, analysis, signal, settings and diagnostic endpoints that are actually present.

Do not assume endpoint paths or schemas.

11.2 Preserve contracts

Unless a separately justified backend bug requires a controlled change:

- Keep endpoint paths unchanged.
- Keep HTTP methods unchanged.
- Preserve request field names and types.
- Preserve response field names and types.
- Preserve status codes and error semantics.
- Preserve authentication headers and cookies.
- Preserve rate limits.
- Preserve request validation.
- Preserve existing business rules.
- Preserve event names and payload schemas.
- Preserve database compatibility.

Do not create a new mock API to make the redesign appear functional.

Do not hardcode sample responses into production components.

Do not silently replace a failing real request with fabricated data.

11.3 Audit API consumers

Search the repository for all usages of the existing endpoints and event streams.

Check:

- API client functions.
- React hooks.
- Server components and client components.
- Polling loops.
- WebSocket/SSE subscriptions.
- Query caching.
- Loading states.
- Error handling.
- Retry behavior.
- Request cancellation.
- Data transformation and formatting.

Where useful, introduce typed API adapters or hooks, but keep the external contracts unchanged.

Avoid duplicating API logic across multiple components.

11.4 Preserve live data behavior

The redesigned dashboard must continue using the actual live market-data pipeline.

- Preserve the current MT5 bridge.
- Preserve "XAUUSDm" mapping.
- Preserve actual candle timestamps and OHLC values.
- Preserve real signal-generation behavior.
- Preserve analysis history.
- Preserve backend connection status.
- Preserve actual stale-data detection.
- Avoid stale caches being displayed as current market data.
- Do not introduce unnecessary polling loops.
- Do not subscribe multiple times to the same event stream.
- Clean up subscriptions when components unmount.
- Prevent late asynchronous responses from overwriting newer data.
- Keep the UI responsive when incoming ticks arrive frequently.

If an API fails, display an honest error or stale state with a retry option where appropriate.

Never make a disconnected backend appear connected just because the new design looks better.
